# Prepared Artifact Performance Baseline

This document records the superseded contiguous-writer baseline captured before the U11
implementation, the supported-workload decision gate, and the metrics preserved by segmented
Prepared Artifacts. Runtime numbers are diagnostic observations from one machine; deterministic
counters and budget ceilings are the conformance contract.

## Code Point

- `e7c8eb9a0e408447f61ae9c937238c16970b4467` is the repository HEAD immediately before the
  Prepared Artifact implementation.
- `crates/unity-asset-write/tests/artifact_characterization.rs` is the reproducible pre-refactor
  sampler and fixture contract.
- The baseline was sampled on `2026-07-19T06:52:09+08:00` before any writer algorithm changed.

## Fixture Contract

| Fixture | Shape | Decision pressure |
|---|---|---|
| `representative-unityfs` | The checked-in `char_118_yuki.ab`, parsed completely and repacked with the original packing policy | Real UnityFS parsing, decompression, member reads, and repacking |
| `generated-large-webfile` | 32 uncompressed one-MiB members | Full-image copy and peak-memory amplification |
| `adversarial-wide-webfile` | 8,192 members with distinct nested names and 17-byte payloads | Per-member allocation and directory-index scaling |

The sampler measures the complete in-memory parse-and-encode operation. Source-file filesystem
reads happen before sampling so operating-system cache noise does not dominate the writer result.

## Metric Semantics

- `allocation_requests` and `allocated_request_bytes` are monotonic calls observed by the test
  executable's global allocator while the operation is active. Reallocation records the newly
  requested size; deallocation is intentionally excluded.
- `peak_rss_growth_bytes` is the process high-water increase between the prepared-input and
  post-operation samples. It includes parser, codec, and writer memory retained during the sample.
- `source_bytes_read` is the encoded input extent plus the logical member payload extent consumed
  again by the legacy writer.
- `decompressed_bytes` comes from the caller-owned `AssetLoadBudget` used by fixture parsing.
- `known_image_materializations` is a code-derived lower bound on full member/image buffers:
  one per copied WebFile member plus its complete output, and one per copied bundle member plus
  the concatenated, compressed, and final bundle images.
- `output_digest` is `DigestV1` over the exact emitted bytes. It is a determinism canary, not a
  golden that prevents intentional wire-correct fixes.
- Short Windows samples may report zero process CPU because `GetProcessTimes` is coarsely
  quantized. Wall time and allocator counters remain available.

## Superseded Aggregate Writer Observations

Measurement host:

- Windows 11 Pro `10.0.26200`, x86-64 MSVC
- Intel Core i9-13900KF, 24 cores / 32 logical processors
- 68,400,455,680 bytes physical memory
- `rustc 1.97.1 (8bab26f4f 2026-07-14)`, LLVM 22.1.6
- release profile, one ignored test process per fixture

|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| representative UnityFS | 704,951 | 3,763 | 718,847 | 717,879 | 239 / 3,663,275 | 1,744,896 | 4 | 1,832,700 | 0 |
| generated large WebFile | 33,555,412 | 33,555,412 | 67,109,844 | 0 | 125 / 133,245,416 | 66,183,168 | 33 | 35,126,900 | 31,250,000 |

The large uncompressed WebFile requests almost four output images' worth of allocation and grows
peak RSS by almost two output images. The wide fixture creates at least one materialized payload
per member. Both are representation failures that the segmented implementation must remove, not
thresholds to preserve.

## Supported Workload Contract

KTD4 is accepted for an in-memory, no-spool proof model under the following default aggregate
ceilings. Callers may choose lower limits. Raising a ceiling requires an explicit policy change;
the implementation must never silently spool or weaken independent proof.

| Resource | Default ceiling |
|---|---:|
| Prepared artifacts | 1,000,000 |
| Logical output bytes | 8 GiB |
| Retained generated bytes | 2 GiB |
| One generated chunk | 1 GiB |
| Generated chunks | 4,000,000 |
| Source ranges / image segments | 4,000,000 |
| Segment and dependency metadata | 512 MiB |
| Uniquely pinned source backing bytes | 16 GiB |
| Peak live build scratch | 2 GiB |
| One compressed stream | 2 GiB retained output |

Parsing and decompression additionally remain subject to the caller-owned `AssetLoadBudget`, whose
default aggregate decompressed ceiling is 16 GiB. Exact-limit and one-byte-over tests are required
for every dimension.

These ceilings deliberately cover the three fixtures with substantial headroom while making the
unavoidable cost of whole-stream LZMA, Gzip, Brotli, or changed compressed bundles explicit. An
artifact whose exact compressed output exceeds retained or live-memory limits is rejected. It is
not written to a temporary file and is not re-encoded during commit.

## Replacement Acceptance Gates

The segmented implementation was accepted against the following gates:

- `full_image_materializations == 0` and `spool_bytes == 0` for Prepared Artifact construction.
- Unchanged SerializedFile objects and uncompressed container members retain their immutable
  source backing instead of copying payload bytes.
- Every affected artifact records exactly one encode, one seal-time DigestV1 traversal, one
  independent reparse, and later one verified publication stream.
- Seek and reads across one-byte segmentation are allocation-free and byte-equivalent to a
  contiguous source.
- SerializedFile, Bundle, and WebFile independent validators consume the same segmented image;
  no validator creates an image-sized contiguous buffer.
- `Preserve` retains signature, version, flags, block layout where valid, directory order, and
  duplicate-member occurrences. Unsupported encrypted or legacy layouts fail structurally rather
  than silently changing flags.
- Randomized request/map order produces byte-identical images, digests, manifests, allocation
  reports, and diagnostics.

## Reproduction

Run the deterministic fixture contract:

```powershell
cargo nextest run -p unity-asset-write --test artifact_characterization `
  legacy_characterization_fixture_contract_is_reproducible
```

Emit each pre-refactor release sample in its own process:

```powershell
cargo nextest run --release -p unity-asset-write --test artifact_characterization `
  prepared_artifact_legacy_sample_representative --run-ignored ignored-only --no-capture
cargo nextest run --release -p unity-asset-write --test artifact_characterization `
  prepared_artifact_legacy_sample_generated_large --run-ignored ignored-only --no-capture
cargo nextest run --release -p unity-asset-write --test artifact_characterization `
  prepared_artifact_legacy_sample_adversarial_wide --run-ignored ignored-only --no-capture
```

Each sampler emits `unity-asset.prepared-artifact-characterization.v1` JSON.
